# Ziggy — operating rules

Ziggy is a per-tenant social media manager: brand → HyperFrames videos → Postproxy posts → inbox →
autopilot. This file is for agents working **on** this repo; `skill/SKILL.md` is for agents
working **with** Ziggy.

## Layout

- `skill/index.js` — the CLI. Thin: argument parsing, output, and the hush re-exec (the child is
  `node` resolved via PATH, overridable with `ZIGGY_NODE_BIN`: `process.execPath` may not exist in
  the filesystem view where hush runs its child). Logic lives in
  `skill/scripts/*.mjs`, each one a module with no side effects on import. `thread.mjs` splits an
  X thread (URL last). `slides.mjs` renders the three 1080×1350 stills.
- `skill/templates/` — HyperFrames templates (`hyperframes/<name>/{host,sub}.html.tpl`) and the
  static social compositions, including `social/slide.html.tpl`. `__TOKEN__` placeholders, filled
  by `video.mjs` / `assets.mjs` / `slides.mjs`.
- `tenants/<slug>/` — versioned tenant definitions. Never put secrets, renders or fonts here —
  and never put **campaigns** here either: `tenants/*/campaigns/` is gitignored, the pipeline
  writes them on disk but story content is not code and must not be pushed.
- `skill/test/` — `node:test`. Every external dependency is faked: mock Postproxy on localhost
  (`helpers.mjs`), fake `hush`, fake agent (`fakeStoryAgent` answers the summary, judge and
  replace prompts apart), fake HyperFrames CLI via `ZIGGY_HYPERFRAMES_BIN`.
- `skill/eval/` — the point judge's eval set and runner, with the real agent: never in `npm test`.

## Rules

- Node ESM, `type: "module"`, no runtime dependencies. Node 20+ (fetch, FormData, `openAsBlob`).
- Output to stdout for the agent; `--json` must stay valid JSON (progress goes to stderr).
- Secrets: never read, print, store or log a key. Keys reach commands only as `POSTPROXY_API_KEY`
  (and `TYPESAFE_API_KEY` for Jev) in the environment, injected by `hush run`. Do not add a config
  field for a key. hush hands a child one secret, so Jev's scoring runs as its own `hush run` child.
- The autopilot asks Jev (`scripts/jev.mjs`, opt-in `autopilot.jev`) before the agent: rules, then
  Jev's sure answers, then the agent. Jev questions stay atomic and literal; a Jev failure must
  leave the item to the agent, never decide it.
- Every backend/API function gets an integration test against the mock server before it ships.
- Run the CLI in tests with `runCli` (async). A `spawnSync` deadlocks the in-process mock server.
- HyperFrames projects generated by `video.mjs` must pass `npx hyperframes check` unchanged:
  one paused GSAP timeline per composition, no CSS-transform/GSAP conflicts, fonts shipped locally,
  `data-layout-allow-overflow` on intentional masks. Test a template change with a real render.
- Keep per-tenant isolation: a command takes one slug and touches only that tenant's paths and secret.
  When several tenants share one Postproxy account, every tenant.json **must** pin its targets:
  `postproxy.profileGroupId` and `postproxy.profileIds` (exact profile ids win over list order in
  `pickProfile` — without them, the first active profile of a platform gets the post, whichever
  tenant it belongs to).
- Story campaigns ask an agent for the reel slides before the campaign is written
  (`story.mjs`: `feed.agent` in tenant.json, same shape as `autopilot.agent`, default
  `claude -p`; `null` disables). The agent prints 3–4 short slides, one story beat per line.
  The agent runs as an async child process (`spawnAgent`), so a round can ask for several stories
  at once. The prompt carries the article (`Article:`) when there is one, the CAN/CANNOT spec,
  and asks for facts the headline and deck do not hold: the list endpoint has no body, so
  `fetchStoryBody` reads the per-story
  endpoint (`storyDetailUrl`: `feed.detailUrl` with `{slug}`, else the list URL's path +
  `/<slug>`, keeping only `lang`; `data.bodyHtml` → plain text, 2,500 characters, 10 s timeout,
  `""` on any failure).
- The reel slides and the caption bullets are **one filtered list**: a point that repeats the
  headline, the dek or an earlier point is a repetition on a slide too, so it is dropped from
  both (`copy.droppedPoints`, each with its reason). The reel keeps up to 4 (`copy.points`), the
  caption the first 3 (`copy.captionPoints`). Two checks, and a point fails when either rejects
  it:
  - **lexical** (`story.mjs` `storyPoints`, i.e. `lint.mjs` `pointsReport` against headline, dek
    and the caption tail): shared content words. It misses paraphrases.
  - **semantic** (`judge.mjs` `judgePoints`): the story's summary agent (`storyAgent`, the same
    command, no other key) gets the headline, the deck, the article and the points in one call,
    and returns JSON per point: similarity to the headline, the deck and each earlier point
    (meaning, 0–1), the new fact in ≤12 words, `grounded`, `generic`. A point passes when its
    highest similarity is under the threshold, it names a new fact, is grounded and not generic.
    Threshold: `tenant.feed.judge.threshold`, else `ZIGGY_JUDGE_THRESHOLD`, else
    `DEFAULT_JUDGE_THRESHOLD` (set from the eval in `skill/eval`). `tenant.feed.judge: false` or
    `ZIGGY_JUDGE=0` turns it off. Any agent or parse failure returns null and the lexical check
    decides alone — never a failed story or round.
  - `refinePoints` runs both, up to 3 rounds: when a point fails, the summary agent replaces
    **only** the failing ones (`buildReplacePrompt`: the list with ✓/✗, why each failed — the
    score and what it repeats, or generic / not in the article / no new fact — the CAN/CANNOT
    spec and the article; passing points stay word for word, in place), and the new list is
    checked again. What still fails after round 3 is dropped. No article: judged and dropped,
    never rewritten. No agent: lexical only, as before. 0–4 points is fine. It returns
    `{ points, kept, dropped, replaced, rewritten, rounds, judgeCalls, rewriteCalls, judge, ms }`.
  This runs in `summarizeStory` (`ziggy story`, the daily loop) and in the round on the
  operator's points. The judge applies to **story points only**: case files (`casefile.mjs`)
  keep their fixed Confirmed / Not confirmed / Why it matters points and only the caption lint.
  The dek is never split into slides (that is the dek told twice): with no points the reel is the
  title slide and the close. Reel length comes from the kept count (~5s title, 4.4s per point, 4s
  close — points must stay readable), never under 13 s: 0 points is title 5 s + close 8 s, 1
  point 13 s, 2 points 18 s.
- **What a point can and cannot say** (`story.mjs` `POINT_SPEC`, Italian and English, in the
  summary, replace and judge prompts; the same text in `skill/SKILL.md`,
  `docs/round-prompt-points.it.md` and `docs/punti-cosa-possono-dire.it.md` — change it in all
  five places). `docs/punti-cosa-possono-dire.it.md` is the standalone Italian spec for editors
  and operators: the spec, the reader's test, the lexical filter and the judge with their
  thresholds and switches, the loop, the eval results and before/after examples.
  - CAN — each point carries at least one, always taken from the article: a number, an amount or
    a quantity; a name (person, organisation, place) that is not in the headline or the deck; a
    date, a time or a deadline; a consequence; a next step (what happens next); a short
    attributed quote or position ("according to…", "…", X said); a concrete detail (the cause,
    the method, where exactly).
  - CANNOT: the headline, the deck or another point in other words (synonyms, reordered, the same
    fact worded more or less specifically); generic commentary or evaluation ("an important
    case", "it remains to be seen"); statements about the sources ("the sources do not say…",
    "no details were given") — they add no fact; facts that are not in the article (no outside
    knowledge, no inference); questions, emoji, hashtags, calls to action. Keep the source's
    hedges.
  - The test: does a reader who already read the headline and the deck learn something new and
    specific from this point? If not, it is a repeat.
- `skill/eval/` holds the judge's eval set (`points-eval.json`, labelled by meaning) and
  `run-points-eval.mjs`, which runs it with the real agent (not part of `npm test`) and writes
  `results/<date>.{json,md}`; `before-after.mjs` runs three of its stories through the real
  `refinePoints` and writes `results/<date>-before-after.{json,md}`. Rerun the eval after
  changing the judge prompt, the spec or the agent, and set `DEFAULT_JUDGE_THRESHOLD` to the
  threshold it recommends.
- Story campaigns are localized per tenant: `tenant.social` holds the caption CTA (placeholders
  `{url}` = the full story link, `{site}` = the display domain) and the hashtags,
  `feed.sections` renames feed sections (e.g. English → Italian), and the
  meta/sources lines follow `tenant.language`. Defaults preserve the original English copy.
  Instagram reels are always on; `tenant.social.platforms` (e.g. `["tiktok", "instagram_post"]`)
  opts a tenant into the extra post kinds — the X thread stays manual (it needs the
  slide-cover still, which the daily loop does not produce).
- Reel audio is generated by `bed.mjs` as a named mood (`MOODS`: `ambient` default, `news`).
  A campaign's `audio.bed` picks the mood; `tenant.social.bed` sets the default for new story
  campaigns. "ambient" stays byte-stable — never change its defaults.
- An X story post always carries the cover image: `posts.twitter.media` is `slide-cover`. Do not
  ship a text-only thread, and do not put the reel on that post instead of the still.
- Story captions are headline, dek, 2–3 summary points, the sources line ("Basato su N fonti in
  M lingue." / "Sourced from N reports in M languages."), CTA and hashtags, one paragraph each;
  the points paragraph has one "• " line per point. Only points with new facts go in (numbers,
  names, dates, what happens next — the summarizer and the round's points read the story body):
  `lint.mjs` `pointsReport` drops a point whose content words (and numbers) are all in the
  headline, dek or an earlier point, one that overlaps the headline ≥ 0.8 or the dek, a dek
  sentence or an earlier point ≥ 0.6, and one that would make the caption fail the lint; the
  semantic judge (`judge.mjs`, above) drops the paraphrases it misses. The
  caption shows the first 3 of the points the reel keeps (the same list, above). 0–1 points is
  fine; with none there is no points paragraph and the caption is headline, dek, sources, CTA,
  hashtags as before. The X thread is unchanged. Every caption is linted before it is scheduled
  or posted (`lint.mjs` `campaignRepetition`: content-word overlap ≥ 0.6 between two sentences,
  ≥ 0.8 against the headline, which a dek legitimately echoes): a round refuses the story or
  case file before the render, `ziggy daily` reports it and leaves the campaign for an editor to
  fix, and `publishCampaign` refuses it on any path. A case file is linted on headline, dek and points,
  without their labels and its `Source:` line, whose URL is dropped when the outlet already names
  it (`casefile.mjs` `sourceLine`). The weekly events caption is a list (towns and venues repeat
  by design) and is not linted. The caption ends with
  the **full story URL** (not clickable on Instagram, but copyable) — there is no comment-LINK/DM
  flow, and no first comment is posted. The autopilot's
  `linkReply` (autopilot.mjs) still exists but is opt-in per tenant.
  `ziggy delete <slug> <postId…>` removes drafts or scheduled posts (no
  media cleanup — recreating a scheduled post re-uploads) and logs a delete event in posts.jsonl.
  `ziggy reschedule <slug> <postId…> --at <ISO>` moves scheduled posts (Postproxy PATCH
  `post.scheduled_at`, accepted until 5 minutes before publish time, no re-upload) and logs a
  reschedule event, so the slot accounting follows the post.
  Published Instagram/TikTok posts cannot be deleted or edited through Postproxy: they go from
  the app.
- `ziggy daily <slug>` (daily.mjs) is the durable daily loop: uncovered feed stories → campaigns
  → rendered reels → scheduled on the tenant's slots (`tenant.json → daily`: slots, tz,
  maxAgeHours, only). An external scheduler (launchd/cron/timer) owns the cadence. Coverage means
  a live post (not deleted) exists in posts.jsonl, matched by slug *and* headline tokens (the
  feed re-slugs stories on update), or a campaign marked `"skip": true` (an editor dropped the
  story, e.g. an event already past). A campaign that crashed mid-run is reused, never
  resummarized. Each story gets the next **free** slot within 24h. A slot holding one of our
  scheduled posts is skipped, and a story with no free slot waits (and may age out): never two
  stories on one slot. The loop hands the story object to `createStoryCampaign`. A second feed
  read can reorder, so an index is not safe. Campaign names that collide with a *different*
  story get the slug's hash appended (`campaignNameFor`). `--dry-run` writes nothing. A story
  whose image URL cannot be fetched fails and is retried on the next tick, so it never renders
  without the photo.
- `ziggy jingle <slug> [--count N]` (music.mjs) adds tracks to the tenant's jingle set, composed
  with ElevenLabs Music from `tenant.json → music.prompt` (instrumental, `music.seconds`, default
  30). The set lives in `brand/jingles/NN.mp3` + `NN.wav` under ZIGGY_HOME, the state volume in
  Docker. `createStoryCampaign` stamps each new campaign with the next jingle in rotation
  (`audio.jingle`, counter in `jingles/rotation.json`), so two stories in a row never share the
  music and re-renders keep theirs. Reels cut it to their own length (`fitJingle`: fade in, 1.8s
  fade out) instead of the synthesized bed; `audio.jingle: false` opts out. The key comes only
  from `ELEVENLABS_API_KEY` via `hush run` (`ZIGGY_ELEVENLABS_API_KEY` in hush), and the Music
  API needs a paid ElevenLabs plan. Never borrow another client's key. Tests fake ElevenLabs on
  localhost (`ZIGGY_ELEVENLABS_BASE_URL`) and ffmpeg (`ZIGGY_FFMPEG_BIN`).
- `ziggy events <slug> --week | --teaser` (events.mjs) renders the week's events reel
  (`eventi-settimana`, campaign `eventi-<monday>` or `eventi-<from>`) or the evergreen events teaser
  (`eventi-teaser`) from `tenant.json → events` (the public events API). It writes a campaign and
  renders reel + post; without `--publish` it never posts. `tenant.events` is read by
  this command (and `events.schedule` by serve) only.
  - Selection: every event of the week (or of `--from … --to …`, an exact range of at most 14
    days, campaign `eventi-<from>`) except `excludeCategories`, `excludeTitles` and the
    conference-type titles in `excludeConferences` (convegni, conferenze, seminari, tavole rotonde,
    workshop, meeting…). One card per event, 2.6 s each, 15–90 s in all; `maxEvents` (40) only
    guards the length. Each card shows the town big and uppercase above the date, the venue small.
    The caption lists every event and drops venues, then the last events, to stay under 2,200 chars.
  - `--week --publish` (eventspub.mjs) then publishes the reel **live, now** on the tenant's
    `daily.only` kinds the campaign defines, one `publishCampaign` call per kind, logged in
    posts.jsonl with the time it went out as `scheduledAt` (`publishedAt`), so the rounds'
    Facebook guard and slots count it. The reel must pass `checkReel` first. `facebook_reel`
    passes `fbAllowed` now (cap, gap, pause after a 368; every live Facebook row counts,
    `scheduledAt || at`) or is held and reported; Instagram goes out anyway. It never drops
    queued posts (the round's job). Idempotent: a platform with a live row of the campaign is
    `already published`, and a re-run reuses the campaign and its renders (`--force` rebuilds,
    still no second post). `--dry-run` shows the plan and posts nothing; `--notify` sends one
    Italian line through `ZIGGY_REPORT_HOOK`. Exit 0 ok (held included), 1 failure/profile
    down/check failed, 3 skipped. The selection is pure and pinned by `test/events.test.mjs` (exclusions,
  merge of recurrences and near-duplicates, score, town spread, max/min, week incl. DST). An end
  at `00:00` is a date (inclusive) except for `events.exclusiveEndSources` (iCal-style). Events
  campaigns carry no `copy.headline`/`story` (the daily coverage reads those) and take no jingle
  from the rotation. Fewer than `minEvents` → exit 3; `--notify` uses `ZIGGY_REPORT_HOOK` only.
- Templates: `story` (one reel per feed story), `teaser` (the original brand teaser) and `intro`
  (a ~10s launch video: a −45° wall of `campaign.images` in a burst, then the brand as it is; see DESIGN.md). Remote images are
  fetched on every scaffold, because assets are named by position and a stale file would
  otherwise keep showing.
- `ziggy report <slug>` (report.mjs) prints a compact emoji digest on stdout: count + last
  permalink of published posts, the next four scheduled slots in the tenant's `daily.tz` (in time order, one line per story even when it goes to Instagram and TikTok together; event lines and deleted posts are never counted, see `readCreatedPosts`; a post removed by hand on the platform — every platform `deleted` — drops out, and only Postproxy `scheduled` posts are queued). It opens with ⚠️ lines for a profile Postproxy reports as not `active` (every post on it fails) and for posts that failed in the last 48h, with the reason
  timezone, one stats line per profile (only non-zero numbers), inbox count + up to three
  comments. A scheduler pipes it wherever (`ZIGGY_REPORT_HOOK='grog telegram-send --to me
  "$ZIGGY_REPORT_TEXT"'` under serve, or a plain cron line). Deleted posts drop out.
- **Operating mode (owner's rule): a Claude session always drives publishing.** No autonomous agent
  and no Anthropic key in the container. Production runs `serve … --no-daily`, which sends
  reports and runs one deterministic job: the weekly events reel (`events --week --publish
  --notify`, Ragusa every Monday at 07:00 Rome, `events.schedule`). Story publishing happens in
  rounds, which a Claude session runs through
  `docker exec ziggy-ziggy-1 node skill/index.js round …`.
- `ziggy round <slug>` (round.mjs) is that round, made deterministic so that any agent given
  the skill does it the same way. The fixed rules for points and skips are in
  `skill/SKILL.md → Running a round`.
  - `--plan` lists the stories not covered and still before their deadline, oldest first, with
    title, dek and `body`: the article from the feed's per-story endpoint as plain text, at most
    1,200 characters, fetched four at a time (`story.mjs` `fetchStoryBody`; a failed fetch is
    `""`, never an error).
  - `--points <file|->` takes `{prefix: [3–4 points], "skip": [prefixes]}`. Points are checked
    (3–4, each at most 90 characters). Stories with no photo, past their deadline, already covered
    or not in the feed are refused before any render. A point that repeats is not a refusal: it
    is dropped from the reel and the caption. The operator's points go through `refinePoints`
    (lexical filter + semantic judge, failing points replaced from the article by the tenant's
    summary agent, up to 3 rounds; body fetched then), three stories at a time; no agent or a
    failing judge leaves the lexical filter alone, and nothing in there fails the round. Each
    result carries `points` (reel), `captionPoints` (at most 3), `dropped`, `rewritten` (a
    replacement is among the kept points), `rounds` and `judge` (`status` on/off/failed,
    `threshold`, `calls`, `rewrites`, `ms`); the summary line reads `· 3 punti (1 scartato)`,
    `· 4 punti (2 giri)`, `· 3 punti (1 scartato, 3 giri)` or `· nessun punto (4 scartati)`.
  - Each campaign gets the next jingle. Reels render in child CLI processes, four at a time, with
    no key in their environment.
  - `checkReel` checks every reel with ffprobe/ffmpeg: rendered, an audio track, mean volume
    above −40 dB, at least 10 s.
  - The good reels are scheduled nearest deadline first, into the next free
    `daily.round.times`, at least `gapMinutes` away from any live post. They go to every
    `daily.only` kind whose Postproxy profile is active; a disconnected one is reported.
  - The summary is Italian, for the owner; `--notify` sends it to Telegram
    (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`).
  - Exit 1 when anything needs a look. `--dry-run` writes, renders and posts nothing. `--now`
    pins the clock for tests.
  - A live round needs a `daily.round` block in tenant.json: the tenant opts into live
    scheduling there.
  - `ensureKey` maps `POSTPROXY_API_KEY_<SLUG>` onto `POSTPROXY_API_KEY` for the command's own
    tenant, so key-needing commands work under `docker exec`.
  - Tenant rules:
    - Ragusa: `freshness: "next-day"`. A story goes out at the latest the day after its news
      date, on the hour 08–23 local, 55 minutes apart. When there are more stories than times,
      they still go out that day, never pushed into the following days.
    - Alien Watch: `freshness: "archive"`. The site publishes one or two stories a day and
      UFO/UAP stories age slowly, so archive stories are welcome (owner's call, 2026-10-09). Its
      six daily times are 85 minutes apart.
    - Both: never publish a story announcing an event that is already past.
- `ops/round/` keeps two tools for the container (`cd /app`):
  - `check.sh <sheet.png> <slug> <campaign>…` prints audio and loudness per reel and writes a
    start/end frame sheet to look at.
  - `notify.mjs "<text>"` sends a free-form message to the operator's Telegram.
- `ziggy serve <slug…>` (server.mjs) is the always-on form of daily + report: one process (or the
  repo's `Dockerfile` + `docker-compose.yml`: keys via `.env.docker`, state volume `ziggy-data`,
  reports to Telegram via `docker/telegram-notify.mjs` as `ZIGGY_REPORT_HOOK`) re-runs each
  tenant's loops on timers (`--every-daily`, `--no-daily` for reports only, `--every-report`,
  `--once`, `--port` → GET /healthz).
  Every run is a child CLI invocation, so keys resolve as usual: in containers via
  `POSTPROXY_API_KEY_<SLUG>` env vars (uppercased slug; the global `POSTPROXY_API_KEY` passes
  through only when serving a single tenant), locally via hush.
  `ZIGGY_REPORT_HOOK` is an optional shell command fired once per report cycle with every
  tenant's digest combined as `ZIGGY_REPORT_TEXT` (blank line between tenants) and
  `ZIGGY_REPORT_TENANT` as the comma list (e.g. a grog send). A failing run is logged in
  `state` and never stops the loop.
  The weekly events job lives in serve too: for each tenant with `tenant.json →
  events.schedule` (`weekday`, `time`, `tz`) a check every minute runs `events <slug> --week
  --publish --notify` as a child, on that weekday from that local time to the end of the day
  (a container down at 07:00 catches up the same day, never later), at most once per ISO week:
  the week goes to `$ZIGGY_HOME/state/<slug>-events-schedule.json` before the run, so a restart
  never repeats it. It runs with `--no-daily`, `--no-events` turns it off, exit 3 (skipped) is
  not an error, and /healthz shows `events.next`. It waits for the same tenant's `daily` run but
  has no lock with a round run via `docker exec`: the two may overlap.
  The image carries everything a render needs — the HyperFrames CLI pinned globally
  (`ZIGGY_HYPERFRAMES_BIN=hyperframes`: an npx download per fresh container raced under
  parallel renders), the headless Chrome (fetched at build time, not on the first story), ffmpeg/ffprobe, `unzip` for puppeteer's browser zip, and the Chromium
  shared libs, and no Claude Code (summaries come from the driving session). A slim base
  missing any one of them fails every render *silently*: the campaign
  stays on disk unfinished and the next tick retries it, so `check ok` in the log is the signal
  that rendering actually works.
  A fresh volume starts with no campaigns; seed `tenants/<slug>/campaigns` into
  `/data/campaigns/<slug>` (the compose header has the command). They are what coverage is
  computed from, so a container without them re-publishes stories that are already out.
- Post kinds live in `publish.mjs` (`POST_KINDS`): twitter, instagram_post/reel/story, tiktok,
  threads, bluesky, linkedin, facebook, facebook_reel (format reel, 3–90s; Postproxy needs the Page id on
  every Facebook post: `tenant.json → postproxy.facebookPageId`, from GET /api/profiles/<id>/placements;
  profile stats need it too, as `placement_id`). TikTok is video-only, always needs media, and its boolean
  params must keep their type: multipart posts send platforms with boolean/number params as one
  JSON `platforms` field; platforms with a `*_file` upload stay flattened.
- Facebook Page guard (`fbguard.mjs`, used by `scheduleRound`): Meta throttles Pages that post too
  often (Graph API 368 / 1390008, "We limit how often you can post"), and every attempt while blocked
  counts again. A round gives a story its Facebook twin only if the Page has fewer than 6 Facebook
  posts that local day, none within 2.5 h, and no 368 in the last 24 h (checked on the recent
  Facebook posts via GET /api/posts/:id). Otherwise the story goes out without Facebook (Instagram
  and the rest unchanged) and the report says so (📘). Tunable with `tenant.daily.facebook`
  (`maxPerDay`, `minGapMinutes`, `pauseHours`, `enabled`; Ragusa: 3/day, 4 h apart, 48 h pause).
  After a 368, every round (even one with nothing new) deletes the Facebook posts already queued
  inside the pause, like `ziggy delete` (delete event in posts.jsonl). Only Facebook-only posts go:
  a post that also carries another platform is flagged, never deleted. The Instagram twins are
  separate posts and stay, so the story stays covered. `--dry-run` only lists them; a failed
  delete is reported and the round goes on. A story gets one Facebook post at most: no twin when
  a live Facebook row exists for its campaign or its story id (`storyIdFromSlug`), this round's
  included (`held` reason `duplicate`).

```bash
cd skill && npm run check && npm test
node skill/index.js doctor <tenant>
node skill/index.js video <tenant> <campaign> --dry-run   # scaffold only
```
